# 拖动预览遮挡播放控件问题复盘

## 结论

播放器收到视频分段请求的 `206 Partial Content` 后，高清拖动预览 Worker 解码出首帧，原本隐藏的预览画布开始显示。画布的层级高于整个 Plyr 根节点，因此把播放控件绘制在了下方。

这不是 `206` 请求失败，也不是控件进入自动隐藏状态，而是一个异步触发的 CSS 层叠上下文问题。

修复提交：`364fedf fix(播放器): 修复拖动预览遮挡播放控件`

## 现象与触发链

- 刚开始拖动时播放控件正常。
- 拖动到一定位置、预览首帧生成后，播放器控件突然消失。
- 鼠标继续移动时进度仍会变化，说明滑块仍在接收拖动操作。
- 同一时间附近，后端会记录素材流接口返回 `206 Partial Content`。

完整触发链如下：

```text
拖动时间滑块
  -> Worker 通过 Range 请求读取视频片段
  -> 后端正常返回 206 Partial Content
  -> Worker 解码出第一张预览帧
  -> has_preview_frame 变为 true
  -> .openvideo_scrub_preview 从 display: none 变为 display: block
  -> 预览画布覆盖 Plyr 根节点及其控件
```

`206 Partial Content` 是视频按字节范围读取时的正常响应。它之所以看起来与故障同步，是因为返回的数据让 Worker 成功生成了首张预览帧，从而激活了真正有问题的覆盖层。

## 根因

修复前的层级关系为：

```text
.openvideo_player
├── canvas.openvideo_scrub_preview  z-index: 2
├── 字幕层                         z-index: 3
└── .plyr                          z-index: 1，形成独立层叠上下文
    └── .plyr__controls            z-index: 3
```

`.plyr__controls` 的 `z-index: 3` 只能在 `.plyr` 自己的层叠上下文中比较。由于整个 `.plyr` 根节点只有 `z-index: 1`，它仍然位于外部预览画布的 `z-index: 2` 之下。提高控件子节点的 `z-index`、`opacity` 或 `visibility` 都无法越过父级层叠上下文。

预览画布设置了 `pointer-events: none`，所以它只在视觉上遮住控件，不会拦截鼠标事件。这正好解释了“图标消失，但继续拖动仍然有效”。

## 为什么之前一直没有检查出来

### 1. 把视觉遮挡误判为控件自动隐藏

故障表现与播放器的自动隐藏很像，之前的修复主要围绕 `opacity`、`visibility`、`transform` 和 `controls.pause()` 展开。这些修改能让控件保持逻辑可见，却无法改变整个 Plyr 根节点低于预览画布的事实。

相关尝试包括：

- `26a7648 fix(播放器): 拖动时保持控件可见`
- `2ec583c fix(播放器): 修复拖动进度条提前隐藏`

### 2. 把 `206` 当成异常方向排查

`206` 容易被误认为视频流被中断或后端响应异常。实际上它是浏览器和解码器读取视频片段的标准响应。真正应该关联的是“收到数据后预览画布首次显示”，而不是状态码本身。

### 3. 预览画布不是一开始就可见

页面初始状态和拖动早期，画布为 `display: none`，DOM 与截图都没有异常。必须持续拖动到 Worker 返回第一帧，并在拖动过程中观察，才能稳定复现遮挡。

### 4. 测试覆盖了状态，没有覆盖真实合成层级

单元测试模拟了播放器组件，能够检查拖动状态、控件暂停和恢复调用，但不会使用浏览器真实计算 Vidstack/Plyr 的层叠上下文。因此即使所有状态断言通过，视觉遮挡仍然存在。

### 5. 已修复过的层级约束在实现替换时丢失

Git 历史显示，这个问题并不是第一次出现：

| 提交 | 变化 | 影响 |
| --- | --- | --- |
| `876326c` | 将旧拖动预览层改为 `z-index: 0` | 已正确认识到预览必须低于 Plyr 根节点 |
| `71ab5f3` | 删除旧拖动预览实现及对应样式 | 层级约束随旧实现一起消失 |
| `562adee` | 接入 Worker 高清取帧画布，并设为 `z-index: 2` | 同类遮挡问题重新引入 |
| `26a7648`、`2ec583c` | 强制保持控件可见 | 修复了可见性状态，没有修复合成层级 |
| `364fedf` | 明确预览、字幕、控件三层顺序 | 从根节点层级解决问题 |

因此，长期没有解决的核心原因是排查一直聚焦“控件为什么隐藏”，而没有先验证“控件是否其实仍然可见，只是被其他图层盖住”。

## 最终修复

播放器图层改为集中管理的语义层级：

```text
预览画布  z-index: 2
字幕层    z-index: 3
Plyr 根层 z-index: 4
```

对应 Token 定义在 `apps/web/src/styles.css`，播放器只引用语义 Token，不再依赖第三方组件默认层级或元素插入顺序。

同时增加 Storybook 回归断言，验证真实计算样式中 Plyr 根层必须高于预览画布。这里必须检查根节点，而不能只检查 `.plyr__controls` 子节点。

## 验证方式

- 使用原问题素材持续向前、向后拖动，直到出现多次 `206` 请求和预览帧更新。
- 在预览画布激活后确认控制条、按钮和时间信息始终可见。
- 确认拖动结束后主画面、播放时间与字幕同步。
- 检查预览画布、字幕层和 Plyr 根层的浏览器计算 `z-index`。
- 运行播放器单元测试、Storybook 测试、TypeScript、ESLint 和构建检查。

## 后续约束

- 新增播放器覆盖层时，必须加入现有语义层级体系。
- 涉及第三方播放器时，必须检查其根节点是否形成层叠上下文。
- 异步显示的图层必须在“激活后”进行浏览器视觉验证。
- 遇到控件消失但交互仍有效时，优先检查覆盖层和 `pointer-events`，不要只检查隐藏状态。
- 视频流出现 `206` 时，先确认它是否为正常 Range 请求，再判断是否存在网络故障。
