# ADR 0004：采用证据优先的统一视频助手与分层多模态检索

- 状态：已接受
- 日期：2026-08-29

## 背景

OpenVideo 的视频问答、总结编辑和转录修正目前以多个 Agent 暴露给用户，并主要依赖顺序字符串匹配读取转录与分析内容。长视频包含大量重复和与问题无关的信息，单次截断上下文、固定数量的顺序结果或只读总结记忆都无法稳定回答跨章节、纯视觉和时间定位问题。总结编辑器传入的任务输入和选区还可能未进入真实模型消息，会产生看似合理但没有消费用户上下文的输出。

产品目标以准确性为硬门槛，同时避免让用户理解内部 Agent、检索器和工具拓扑。

## 决策

### 统一助手与确定性工作流

用户只看到一个全局助手。视频问答、总结编辑、转录修正、索引和媒体处理保留为内部能力：模型负责理解意图与选择能力，转录、索引、版本提交和批量修改由确定性工作流执行。内部任务可以并行，用户无需先选择 Agent。

对话绑定到“视频、内部能力、当前文档或任务”。切换工作对象时必须切换或新建匹配会话，禁止仅按视频复用不匹配的上下文。默认检索当前视频；只有用户通过自然语言或范围控件明确要求时，当前问题才可检索已分析的资料库。跨视频证据必须标注素材与时间范围，下一轮默认恢复当前视频范围。

### 上下文附件

字幕、总结和时间线选区使用统一的显式附件契约。用户可拖放选中文字、使用“添加给 AI”操作，或把时间线范围加入输入。附件始终可见、可删除，并绑定到发送时的内容版本。历史回答保留发送时快照；任何写入操作在提交前重新读取最新版。

时间线附件只保存范围引用，不复制范围内全部内容。运行时按问题需要读取字幕、OCR、关键帧和音频证据。每个持久化附件标识使用带语义前缀的 UUIDv7。

### 证据优先的分层多模态检索

检索层采用分层多模态 Agentic RAG，而不是“文本切块后取固定 Top-K”：

```text
视频
→ 章节
→ 场景或事件
→ 时间片段
→ 字幕句、OCR、关键帧与音频证据
```

查询先限定素材、版本和显式时间范围，再并行执行 SQLite FTS5 关键词检索、语义检索、元数据过滤和已验证记忆检索。候选结果经过合并、去重与重排，然后扩展相邻时间窗口验证画面。证据不足时允许有限次数的补充检索，禁止无上限 Agent 循环。

已验证项目记忆只用于理解意图、扩展查询和定位范围，不能替代原始证据。媒体元数据和成功执行结果等确定事实可自动进入项目记忆；模型推断只有在用户确认后才能长期保存。事实与媒体、转录及分析版本绑定，来源变化后自动失效。

### 本地索引与渐进初始化

SQLite 是唯一持久化检索数据库，不要求用户启动独立向量服务。FTS5 提供词法检索；语义向量保存在 SQLite，由进程内检索器读取。初期优先在当前视频的限定候选集上执行精确检索，资料库规模需要时再评估 SQLite 向量扩展，不能为了向量检索引入常驻服务。

语义模型由 OpenVideo 提供经过评测的精简推荐目录，用户选择已注册模型。模型首次使用时按需下载到用户配置目录。索引记录模型、版本、向量维度和内容版本；切换模型时后台构建新索引，旧索引保持可用直到新索引原子切换。

视频导入后在后台渐进建立转录、章节、OCR、关键帧和检索索引。界面展示真实阶段与覆盖范围。已有证据足够的局部问题可以先回答；全片统计和跨章节结论在覆盖不足时不得把“尚未索引”解释为“不存在”。来源更新后只重建受影响片段及其上层索引。

转录、OCR、镜头切分、关键帧和索引默认在本地执行。大语言模型和视觉模型使用用户注册的在线 API。后台初始化不调用视觉 API 扫描整部视频；视觉问题先用本地索引定位候选片段，再发送最少证据验证。视觉结果以视频版本、时间范围、模型和提示版本为键保存结构化缓存，重要或冲突问题仍需重新验证。

### 证据与置信度

每个事实性回答都必须保存证据引用。置信度只使用高、中、低三档，由确定性证据评分器根据检索匹配、时间覆盖、来源一致性和冲突计算，模型不得自行提高置信度。

- 高、中置信度默认显示精简的已参考内容，证据详情折叠。
- 低置信度查询可以给出暂定结论，但必须主动展开相关或冲突证据。
- 低置信度修改停止执行，一次只询问一个关键问题。
- 字幕、OCR、画面与分析冲突时先检索相邻窗口和其他来源；仍冲突则并列展示，不得静默选择。

回答正确必须同时满足结论正确与证据确实支持结论。用户满意度只能在通过准确性硬门槛后用于选择更快、更简洁的实现。

### 不可信内容边界

字幕、OCR、画面文字、转录和检索结果都是不可信证据。模型可以理解其语义和识别其中描述的命令，但它们不能改变系统指令、权限或工具策略。当前版本不提供互联网检索；外部知识检索作为后续 ADR 议题，不进入本期实现。

## 共享运行契约

每次运行输入至少包含：用户内容、`auto`/`fast`/`complex` 模式、显式上下文附件、当前检索范围和任务输入。非空用户内容不能导致任务输入或附件被丢弃。

每条证据引用至少包含：证据标识、素材标识、来源类型、来源版本、起止时间、可展示摘要和支持或冲突关系。每条回答至少包含：正文、确定性置信度、证据引用和运行指标引用。任何持久化标识使用统一 UUIDv7 工具生成。

## 被否决的方案

- 把整部视频和所有分析一次性塞入长上下文：成本高、噪声大，并会遗漏上下文中部证据。
- 只使用顺序字幕字符串匹配：无法稳定处理同义表达、纯视觉事件和全片覆盖问题。
- 以项目记忆替代转录和画面检索：记忆可能过期或省略关键细节。
- 默认跨资料库检索：容易把其他视频内容误认为当前视频事实。
- 后台调用视觉模型扫描全部关键帧：长视频费用和等待时间不可控。

## 结果

- AI 输出能够证明实际消费了用户附件、当前版本和视频证据。
- 长视频检索从固定顺序结果升级为带时间覆盖的分层检索。
- 用户获得统一助手体验，内部仍保留可测试的专业工作流。
- 本地渐进索引不阻塞打开视频，也不引入额外数据库服务。
